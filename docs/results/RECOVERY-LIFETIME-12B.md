# WM-012B — 복구 창 반복 수명과 대기 측정

2026-10-22, 0.9.8 prototype, Windows x64 10.0.26300 / .NET SDK 10.0.401, 논리 CPU 8개. 제품 코드·버전·저장 형식 변경 없이 별도 실행형 검증을 추가한다. 실제 사용자 메모, 실행 중인 앱, 시스템 보안 설정을 변경하지 않는다.

## 시험 방법

`--recovery-probe`는 출력 폴더 아래 실행별 GUID 디렉터리에 숨긴 메모 1개와 같은 암호화 내용의 임시 후보 65개를 만든다. 실제 `PendingRecoveryWindow`, `NoteWorkspace`, DPAPI 저장소와 컨트롤 이벤트를 사용한다. `WindowInteropHelper.EnsureHandle()`로 네이티브 창 핸들도 생성하지만 `Show()`는 호출하지 않는다. 화면 표시·포커스·Loaded·실제 마우스/키보드 입력을 시험한 것은 아니다. 숨긴 메모만 사용하므로 바탕화면 메모 표면은 생성하지 않는다.

10회 워밍업 뒤 다음 순서를 100회 반복한다.

1. 복구 창 생성 → 첫 64개 목록 → 실제 파일 읽기·복호화·RTF 미리보기.
2. 합성 사본의 저장 대상에 빈 디렉터리를 만들어 실제 새 파일 쓰기를 실패시킨다.
3. 복구 버튼과 재시도 버튼을 각각 실행하고 선택·읽기 전용 미리보기·저장 메모 수를 확인한다.
4. 다음 1개 항목으로 이동해 이전 미리보기 해제 → 처음부터 확인 → 커서가 남은 창 닫기.
5. 시험용 빈 디렉터리 제거. 10회마다 약한 참조, GC 후 관리 힙, Private Bytes, 프로세스 핸들, GDI·USER를 기록한다.

반복 전후 파일 목록·SHA-256·수정 시각이 같아야 한다. 별도의 복구 창을 저장 실패 미리보기 상태로 300초 유지하며 30초마다 강제 GC 없이 측정한다. 대기 전후 파일 불변을 확인하고, 장애를 제거한 뒤 같은 미리보기의 재시도로 사본 1개 저장·선택 해제·원본 65개 보존을 확인한다. 마지막 창과 문서도 회수 가능해야 한다.

측정 경계의 강제 GC는 시험 코드에만 있다. 제품에 주기적 GC·작업 집합 축소·자동 재시작을 추가하지 않는다. 프로세스 핸들 +12 / GDI·USER 각 +4 초과, 잔존 창·문서, 관리 힙 증가가 기준값의 20% 또는 10MiB 중 큰 값 초과 시 시험을 실패시킨다. Private Bytes는 기록하고 추세를 검토하며 단일 증가만으로 누수라고 판정하지 않는다. 기준 이하라도 지속적인 증가 추세가 보이면 추가 조사한다.

## 관측 결과

100회 반복과 300초 대기, 대기 후 실제 저장 재시도 PASS. 각 반복 측정 구간 및 마지막 닫기 후 잔존 창·문서 참조는 0개다. 대기 중 파일 목록·해시·수정 시각이 유지됐고, 마지막 복구에서 사본 1개만 추가되고 원본은 유지됐다.

| 시점 | GC 후 관리 메모리 MiB | Private Bytes MiB | 프로세스 핸들 | GDI / USER |
| --- | ---: | ---: | ---: | --- |
| 워밍업 후 | 1.856 | 86.168 | 505 | 10 / 16 |
| 50회 닫기 후 | 1.927 | 89.238 | 507 | 10 / 16 |
| 100회 닫기 후 | 1.931 | 94.012 | 509 | 10 / 16 |
| 실패 미리보기 대기 시작 | 1.957 | 91.332 | 489 | 16 / 18 |
| 5분 대기 후, 창 유지 | 1.994 | 82.875 | 485 | 16 / 17 |
| 저장 재시도·창 닫기 후 | 2.112 | 83.328 | 483 | 10 / 12 |

대기 300.0215초의 프로세스 CPU 시간은 6,562.5ms, 한 코어 기준 2.1873%, 논리 CPU 8개 전체 기준 **0.2734%**였다. 첫 비표시 네이티브 창의 지연 작업·JSON 측정/출력 비용도 포함한다. 작업 관리자의 특정 순간 값이 아니라 CPU 시간 차이를 실제 경과 시간과 논리 CPU 수로 나눈 평균이다.

대기 중 강제 GC 전 핸들 수는 최대 551개까지 증가했으나 대기 종료 GC 후 485개, 마지막 창 닫기 후 483개로 내려왔다. Private Bytes도 반복 중 증가 뒤 감소했다. 측정 도구·런타임·WPF 중 어느 항목이 각 변동을 만들었는지 모두 규명하지는 않았다. 같은 닫힘 상태의 비교와 약한 참조에서 지속 누적 징후는 관찰되지 않았으며, 장시간 무누수 판정으로 확대하지 않는다. 제품에 누수를 감추는 최적화는 추가하지 않았다.

로컬 원본 로그(artifacts는 Git 제외):

`artifacts/recovery-lifetime-validation/bin/WindowsMemo.Tests/release/recovery-probe/6fe286fce5fa42838774ebf3fd67171b/metrics.jsonl`

최종 파일 개수까지 검사하는 단언 보완 전 위 100회/300초를 실행했다. 해당 실행의 최종 파일을 별도로 세어 본체 2개·원본 임시 파일 65개·백업 0개, 총 67개임을 확인했다. 최종 코드도 CI와 같은 5회/1초 smoke PASS이며 로그는 같은 `recovery-probe` 아래 `395cee28c9fb48f7bb1b3b9feabe24c2/metrics.jsonl`이다. 짧은 smoke는 별도 중단 복구 시험과 동시에 실행했으므로 CPU 측정 근거로 사용하지 않는다.

최종 Release 빌드는 경고·오류 0, 기존 전체 로컬 **118개** 검사(자동 117개 + 실제 비표시 셸 호스트 1개)와 격리 자식 중단 복구 **10건** 모두 PASS다. 중단 복구 JSONL은 같은 출력 경로의 `crash-probe/a213c7eb55d044d9b9212ec4de93bb8e/results.jsonl`에 남겼다. 새 probe는 별도 명령이므로 기존 검사 개수를 늘려 표시하지 않는다.

## 재현

```powershell
dotnet build WindowsMemo.slnx --configuration Release -p:RestoreLockedMode=true --artifacts-path artifacts/recovery-lifetime-validation

dotnet artifacts/recovery-lifetime-validation/bin/WindowsMemo.Tests/release/WindowsMemo.Tests.dll --recovery-probe --cycles 100 --idle-seconds 300
```

옵션은 `--cycles 1..1000`, `--idle-seconds 0..86400`이며 기본 100회/300초다. 중복·누락·알 수 없는 옵션과 범위 밖 값은 실행 전에 거부한다. 시작 JSON의 `run` 폴더에 시험용 Notes와 `metrics.jsonl`을 남긴다. 시험 본문·예외 원문은 측정 로그에 넣지 않는다. 실행 경로와 프로세스 번호는 로컬 진단 메타데이터로 기록한다.

Windows CI는 5회/1초 smoke를 실행하고 `recovery-lifetime-metrics` artifact를 14일 보관한다. 이 짧은 실행의 CPU 수치를 5분 유휴 측정으로 해석하지 않는다.

## 남은 확인

보이는 창의 실제 입력·한글 조합·접근성·혼합 DPI, Win+D, Explorer·절전 복귀, 설치본, 실제 저장 공간 부족·권한 조합, 8/24시간 전체 앱 상주는 포함하지 않는다. 짧은 구성요소 시험으로 앱 전체의 무누수·무취약점을 보증하지 않는다. 실제 데이터·형식·UI를 바꿀 필요가 있는 누적 문제를 발견했을 때만 원인에 맞는 제품 수정을 진행한다.

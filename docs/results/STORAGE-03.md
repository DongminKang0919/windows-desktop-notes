# 0.3.0 메모 저장·복원 검증

- 작업: WM-004의 메모 하나 저장·복원 단계 및 WM-011 관련 저장 보호
- 날짜: 2026-10-13
- 환경: 기존 검증 PC, Windows 빌드 26200.9457 / x64, .NET SDK 10.0.401
- 상태: 구현·자동 검증 완료, 실제 앱 수동 검토 대기

## 구현 범위

본문 RTF와 화면 위치·크기를 내부 레코드로 직렬화하고 Windows DPAPI CurrentUser로 암호화한다. Windows Desktop 공유 프레임워크에 포함된 System.Security.Cryptography.ProtectedData를 사용하며 별도 NuGet 패키지를 추가하지 않았다.

저장 폴더는 %LOCALAPPDATA%\WindowsMemo\Notes다. 일반 창 진단은 Diagnostic 하위 폴더를 사용한다. 현재 메모 하나를 관리하므로 앱이 정한 고정 GUID를 파일명으로 사용한다. 여러 메모로 확장할 때 각각의 ID를 부여한다.

편집·서식·위치 변경 뒤 500ms 지연, 연속 변경 시 최대 5초 대기 기준으로 저장한다. UI 디스패처에서 RTF 스냅샷을 생성하고 작업 스레드에서 암호화·파일 작업을 한다. 저장은 직렬화하며 변경 버전을 추적한다. 이전 저장 완료가 새 변경을 저장 완료로 표시하지 않는다. 실패 시 5초 뒤 자동 재시도와 수동 재시도를 제공한다.

닫기는 최신 변경을 저장한 뒤 종료한다. 실패하면 종료를 취소하고 편집기를 유지한다. 숨김·트레이 동작은 WM-007에서 구현할 예정이다.

## 파일 보호

- 봉투 버전 1, DPAPI-CurrentUser 표시, 암호문만 외부 JSON에 기록
- 내부 스키마 1, 고정 ID, RTF, 위치·크기, 생성·수정 시간 검증
- 임시 파일도 암호화된 결과만 쓰고 Flush(true) 및 닫기 후 File.Replace로 교체
- 이전 파일 하나를 .bak으로 보관; 첫 저장은 File.Move 사용
- 손상 원본은 백업을 읽어 복구; 이후 저장 시 .damaged-GUID로 보존하고 정상 백업을 유지
- 백업만 남은 경우에도 복구 시도; 모두 실패하면 새 빈 메모로 덮어쓰지 않음
- 저장 루트의 조상과 본체·백업의 재분석 지점 거부. 파일명은 앱 내부에서 생성
- 파일 4MiB, 내부 JSON 3MiB, RTF 2MiB, JSON 깊이 16, 본문 100,000자 제한
- RTF 파싱 전 개체·그림·필드·바이너리 제어어 및 과도한 중첩 거부, 복원 후 허용 문서 요소 검사

일반 텍스트의 역슬래시와 중괄호는 RTF 이스케이프를 구분해 정상 왕복한다. 파일 경로의 같은 계정 공격자가 검사와 쓰기 사이를 바꾸는 경쟁 조건을 완전히 방어하지는 않는다. 원본 보존 파일은 자동 삭제하지 않는다.

참고: [Microsoft DPAPI 안내](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection), [File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace).

## 실행 결과

Release 솔루션 빌드: 경고 0, 오류 0.

최종 명령:

```powershell
dotnet tests/WindowsMemo.Tests/bin/Release/net10.0-windows/WindowsMemo.Tests.dll --shell-probe
```

**27개 통과, 종료 코드 0.** 기존 18개 검증, 신규 저장 검증 8개, 실제 바탕화면 호스트 생성·해제 1개다.

신규 검증은 한글·굵게·색상·번호 목록 RTF 왕복, 암호화 저장과 위치 복원, 백업 생성, 손상 본체 보존, 암호문 변조·초과 크기·스키마·ID·좌표 거부, RTF 손상 시 백업 복구, 파일 잠금으로 유발한 쓰기 실패와 재시도, 저장 도중 추가 입력 및 서식만 변경 시 저장을 포함한다. 모든 시험 파일은 테스트의 bin 하위 폴더에 생성했다. 사용자 데이터 폴더는 사용하지 않았다.

검증 중 손상 데이터 예외 분류 누락을 발견해 InvalidDataException을 추가했다. 테스트의 비동기 저장에는 실제 WPF와 같은 DispatcherSynchronizationContext를 적용했다. 수정 뒤 전체 검증이 통과했다.

이전 0.2.0 기록의 앱 제어 정책 차단과 별개로 이번 최종 0.3.0 테스트 DLL은 같은 PC에서 정상 로드·실행됐다. 보안 설정은 변경하지 않았다.

## 남은 확인

- 실제 앱에서 메모·서식·이동·크기를 변경하고 저장 완료 후 종료·재실행
- Win+D·한글 조합·서식 도구 포커스의 0.3.0 회귀
- 실제 탐색기 재시작, 여러 모니터·혼합 배율, 절전 복귀
- 다른 Windows 사용자 계정에서 복호화 실패 확인
- 강제 종료·전원 중단 및 디스크 공간 부족에 대한 실제 파일 시스템 복구
- 연속 입력 시 지연·최대 대기 시간의 실제 UI 동작, 반복·장시간 리소스 측정
- WM-007의 숨김 상태 저장 및 복원

자동 검증은 실제 IME나 Win+D의 화면 동작, 제품 전체 보안·안정성 검토를 대신하지 않는다.

## 해석과 남은 확인

측정 대상 프로세스가 8시간 동안 유지됐고 샘플 수집이 완료됐다. 메모 개수·보이는 상태·시험 중 사용자 조작과 절전 여부는 측정 로그에 기록되지 않았다. 저장 파일 해시, 네트워크 활동, 관리 힙, 앱 응답성, 내용·서식의 보존 및 정상 종료·재실행은 이 도구가 검증하지 않았다. 따라서 이것만으로 전체 실사용 시험 통과, 데이터 보존 또는 무누수를 판정하지 않는다. 실제 UI와 데이터 확인, 반복 조작, 24시간 시험 및 새 버전의 별도 측정은 남아 있다.

빌드와 자동 검사: 별도 출력 폴더에 Release 빌드 성공(경고·오류 0), 사용자 환경의 자동 검사 154개 통과. Win+D·IME·화면 동작은 자동 검사 범위 밖이다.

## 원시 자료 재분석 — 2026-11-19

원격 `main`의 `d4ad115`에 포함된 CSV 481행을 요약 JSON 및 측정 스크립트와 대조했다. 아래 값은 원시 자료를 다시 계산한 결과다. 위의 빌드·154개 자동 검사 기록은 데스크톱에서 수행한 기존 기록이며 이번 분석에서 재실행한 검사가 아니다.

### 수집 연속성

- CSV 481개와 JSON의 `sample_count`가 일치한다. 첫 CPU 구간 값의 의도된 빈칸 외에 수치 결측·비정상 값은 없고, 중복 시각·경과 시간 역행·누적 CPU 감소도 없다.
- 인접 표본 480구간의 간격은 52.694~60.048초다. 마지막 구간만 52.694초로 짧다. 스크립트는 표본 처리 후 60초씩 대기하다가 목표 종료 시각에 맞춰 마지막 대기를 줄이므로, 이 패턴은 수집 방식과 부합한다.
- 첫 표본부터 마지막 표본까지 경과 시간은 28,799.995초이고 JSON의 전체 실행 시간은 28,800.013초다. 시작·마무리 처리 시간 때문에 측정 범위가 약간 다르다.
- UTC 시각 차이로 계산한 표본 간격도 52.694~60.048초다. 로그상 큰 수집 공백은 없지만 전원 이벤트가 없어 절전 여부 자체를 확정하지는 않는다.

### 자원 변화

MiB는 1,048,576 bytes다.

| 지표 | 시작 | 종료 | 변화 | 전체 범위 |
| --- | ---: | ---: | ---: | ---: |
| Private MiB | 64.691 | 64.492 | -0.199 | 64.398~64.691 |
| Working Set MiB | 123.313 | 123.473 | +0.160 | 123.180~123.813 |
| 프로세스 핸들 | 650 | 549 | -101 | 549~650 |

- 핸들은 약 35분에 638→549개로 감소했다. 약 77분에 552개가 됐다가 다음 표본에 549개로 돌아왔으며 이후 끝까지 549개다. 감소한 핸들의 종류나 원인은 이 자료로 알 수 없다.
- USER는 약 8분 이후 31개, GDI는 전체 구간 25개로 유지됐다.
- 첫 2시간 이후 Private Bytes의 전체 변동 폭은 86,016 bytes(84KiB), 작업 집합은 49,152 bytes(48KiB)다. 작은 등락은 있지만 시간이 지날수록 자원이 쌓이는 패턴은 관찰되지 않는다.

### CPU

CSV의 반올림된 구간 퍼센트를 평균내지 않고 누적 CPU 차이를 실제 경과 시간과 논리 CPU 12개로 나누었다.

`전체 시스템 기준 평균 CPU(%) = 100 × CPU 누적 시간 차이 / 경과 초 / 12`

- 전체 CPU 누적 증가: 0.297초. 전체 시스템 기준 평균 약 **0.000086%**, 단일 논리 CPU 기준 약 0.001031%다.
- 첫 5분을 제외한 평균은 약 0.000064%다. 사용자 조작 표시가 없어 이를 확인된 유휴 구간이라고 부르지는 않는다.
- 인접 5개 구간(약 5분)의 이동 평균 최댓값은 약 **0.002166%**다. 저장소의 유휴 5분 조사 기준인 1%보다 낮지만, 실제 유휴 여부의 별도 확인은 필요하다.
- 480개 CPU 구간 중 462개는 기록값이 0이다. CPU 누적 초는 소수 셋째 자리, 구간 퍼센트는 넷째 자리로 반올림되므로 이를 CPU 사용이 전혀 없었다는 뜻으로 해석하지 않는다. 짧은 순간의 CPU 급증도 60초 표본으로 구분할 수 없다.

### 판단과 다음 확인

이번 기록은 **0.9.16 프로세스의 8시간 상주 완료와 측정 자원의 안정적인 추세**를 뒷받침한다. 기존 요약의 시작·종료·최솟값·최댓값·CPU 수치를 재계산한 결과도 일치했다. 현재 자료에서 자원 증가 문제를 특정해 코드 수정을 시작할 근거는 발견되지 않았다.

현재 0.10.0에는 이후 바탕화면 표시 복구 및 설정·제목 변경이 포함되므로 이번 결과를 현재 버전의 시험 통과로 옮기지 않는다. 다음 검증은 다음 순서가 적절하다.

1. 0.10.0을 최신 [장시간 감시 도구](../LONG-RUN-TEST.md)로 8시간 측정한다. 실행 버전·해시, UI 응답 참고값, 앱 종료·재시작 및 표본 공백을 함께 남긴다.
2. 메모 개수와 표시 상태를 기록하고 I/A로 유휴·사용 구간을 나눈다. 편집·저장·숨김·재표시·목록·설정·제목 변경을 수행한 뒤 같은 메모/창 수의 유휴 상태로 돌아와 자원 추세를 비교한다.
3. 정상 종료 후 재실행하여 본문·서식·제목·위치·상태 보존을 직접 확인하고, 24시간 측정을 이어 간다. Win+D·Explorer 재시작·절전 복귀는 해당 조작과 시각을 별도 기록한다.

# 메모리 및 시스템 안정성 설계

현재 prototype에서 창 훅·이벤트 해제 및 Dispose를 구현했다. 아래에 기록한 반복·대기 측정과 향후 장시간 시험 계획을 구분한다. 짧은 시험의 참조 회수·핸들 안정만으로 장시간 누수 부재를 보장하지 않는다.

0.2.0에서는 복구 타이머·알림용 창·임시 창의 소유와 정리를 구현하고 가짜 부모 창 20회 교체 및 호스트·편집기의 수집 가능 여부를 확인했다. 실제 탐색기 재시작이나 장시간 무누수 검증으로 확대 해석하지 않는다.

## 2026-10-22 중간 점검

0.9.1은 저장 완료 후 자동 저장 타이머를 멈추며 새 변경이 있을 때 다시 시작한다. 저장 실패 안내는 새 입력으로 숨기지 않고 성공까지 유지한다. 입력 한도 검사와 제목 갱신은 하나의 본문 읽기를 공유하고, 브러시·글꼴은 재사용한다. 바탕화면 이동 시 둥근 영역을 크기/배율 변경 없이 다시 만들지 않으며 저장 좌표가 같으면 변경을 발행하지 않는다.

복구 타이머·알림 창·자동 저장 타이머를 가진 시험 메모 세션 2,200개를 생성·폐기했다. 측정 두 구간 모두 잔존 세션/편집기 참조 0개, GDI 44 / USER 18로 기준값을 유지했다. 관리 메모리는 1.98→2.03→2.19MiB, Private Bytes는 138.44→155.89→160.91MiB였다. 짧은 반복 시험에서 객체·GDI/USER 누적 징후는 관찰하지 못했지만 Private Bytes 증가의 장시간 추세와 8/24시간·idle CPU 시험은 남아 있다. [재현 방법과 전체 수치](results/REVIEW-14.md).

## 리소스 수명

0.9.8 복구 창도 10회 워밍업 후 100회 열기·실패 재시도·64+1 탐색·닫기와 5분 실패 미리보기 대기를 측정했다. 매 구간 폐기 창·문서 참조 0개, GDI/USER 누적 징후 없음, 대기 CPU는 논리 CPU 8개 전체 기준 0.2734%였다. 원본 파일 불변과 대기 후 사본 1개 저장을 확인했다. 대기 중 일시적인 핸들 증가와 종료 후 감소도 숨기지 않고 [측정 기록](results/RECOVERY-LIFETIME-12B.md)에 구분했다. 실제 표시·입력·Loaded와 8/24시간 전체 앱 검증은 남아 있다.

| 소유자 | 리소스 | 종료·해제 규칙 |
| --- | --- | --- |
| 앱 | 트레이 아이콘, 시스템 이벤트, 단일 실행 핸들, 공용 네트워크 클라이언트 | 종료 시 이벤트 해제 및 IDisposable 정리 |
| 메모 창 | HWND 훅, 편집기 문서, 서식 상태, 창 이벤트 | 실제 창 폐기 시 훅·이벤트·참조 정리 |
| 자동 저장 서비스 | 타이머, 취소 토큰, 저장 작업, 스냅샷 | 중복 타이머 금지. 종료 시 취소·작업 완료 확인·정리 |
| 부착 서비스 | Win32 훅, 콜백 델리게이트, 탐색기 탐색·복구 작업 | 재부착 시 이전 연결 해제. 새 연결을 누적하지 않음 |
| 파일 저장소 | 스트림, 임시 파일 | 성공·오류 모두 스트림 닫기. 사용 중 파일을 무작정 정리하지 않음 |

숨김과 실제 폐기는 구분한다. 숨긴 메모는 최신 상태 저장 성공 후 편집기와 창을 폐기하고 다시 표시할 때 복원하는 방식을 기본으로 한다. 저장 실패 시 메모리의 최신 내용은 보존하며 '숨겼으니 정리해도 된다'고 취급하지 않는다. 삭제·영구 삭제는 저장 중 작업과 경합하지 않도록 순서를 조정한다.

이벤트 구독은 소유자와 해제 시점을 명시한다. 장수 서비스·정적 이벤트가 창을 붙잡지 않게 한다. 필요할 때 WPF weak event를 사용하되 명확한 해제와 Dispose를 대체한다고 가정하지 않는다. Win32 HWND는 소유권을 구분하고 탐색기 소유 창을 앱이 파괴하지 않는다.

참고: [Microsoft WPF weak event](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/events/weak-event-patterns).

## 무한 증가 및 과도한 작업 방지

- 자동 저장 큐는 메모별로 최신 대기 스냅샷 하나로 합친다. 오래된 전체 문서 복사본을 무제한 보관하지 않는다.
- Undo 기록은 유한 개수로 제한한다. 초기 후보는 100단계이며 대용량 입력을 포함해 측정한다.
- 메모 목록은 전체 편집기를 생성하지 않고 필요한 상태만 읽는다. 숨긴 메모 전체를 FlowDocument로 유지하지 않는다.
- 업데이트 확인·부착 복구는 중복 실행하지 않는다. 재시도 간격과 최대 횟수를 두고 실패마다 즉시 반복하지 않는다.
- 파일·로그·임시 파일·다운로드 캐시가 누적되지 않도록 보관 한도를 정한다. 휴지통은 사용자 데이터이므로 자동으로 지우지 않는다.
- UI 스레드에서 네트워크·파일 대기 또는 `.Wait()`/`.Result`로 작업을 막지 않는다. 문서 직렬화는 UI 스레드가 필요한 범위를 제한하고 그 비용을 측정한다.
- Win32 호출은 반환값, 마지막 오류, 핸들 유효성을 확인한다. 탐색기 응답에 무한정 기다리지 않도록 시간 제한을 사용하는 호출 방식을 검토한다.
- 부착 복구가 실패해도 CPU를 계속 사용하지 않고 재시도 또는 오류 상태로 전환한다.
- 누수를 숨기기 위해 주기적인 강제 GC, 작업 집합 강제 축소, 자동 앱 재시작을 넣지 않는다.

## 오류와 데이터 보존

취소와 실제 오류를 구분하고 작업 예외를 관찰한다. 모든 예외를 잡아 성공으로 진행하지 않는다. 오류는 작업 단위로 처리하며 저장이 실패한 메모의 최신 내용을 지키는 것을 우선한다. 손상 문서 하나가 다른 메모를 덮어쓰지 않게 한다.

디스크 공간 부족·쓰기 권한 실패·복호화 실패·프로세스 중복·탐색기 재시작·절전 복귀를 시험한다. 시스템 종료나 정전에서는 앱에 충분한 시간이 없을 수 있으므로 직전 미저장 내용까지 보존한다고 약속하지 않는다.

## 누수 검증 절차

Release 빌드의 설치 또는 실행 방법을 고정하고 가짜 메모 데이터를 사용한다. 버전, OS, 화면 배율, 모니터, 입력 크기와 작업 수를 기록한다.

1. 시작 후 5분 워밍업하여 기본 상태를 측정한다.
2. 메모 10개 생성 → 입력·서식 수정 → 숨김 → 재표시 → 삭제·폐기 사이클을 100회 수행한다. 숨겨진 데이터나 휴지통 항목이 실제 늘어나지 않는 조건도 별도로 만든다.
3. 같은 최종 메모 수와 창 수로 돌아온 뒤 5분 안정화한다. 반복 실험을 두 번 수행한다.
4. 작업 집합, private bytes, GC 힙, Window·FlowDocument 객체 수, 프로세스 핸들·GDI·USER 개수, 스레드 수와 CPU를 비교한다.
5. 의도적으로 폐기한 창의 참조가 해제되어 수집 가능한지 스냅샷과 참조 경로로 확인한다. 캐시·JIT·GC 유보에 따른 증가와 계속 남는 참조를 구분한다.
6. 안정 상태에서도 반복마다 증가한다면 메모리 덤프 등으로 참조 소유자를 추적한다. 필요 시 진단 환경에서만 GC 후 비교한다.

작업 집합이 즉시 내려가지 않는 것만으로 누수라고 판정하지 않는다. 네이티브 핸들 누수는 관리 힙 측정만으로 찾을 수 없으므로 별도 지표를 함께 본다. 도구 후보는 Visual Studio 메모리 분석, dotnet-counters, dotnet-dump 및 Windows 리소스 측정이다. 설치된 도구와 .NET 버전 확인 후 실제 명령을 기록한다.

참고: [Microsoft .NET 누수 진단](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-memory-leak).

## 장시간 및 시스템 시험

- 첫 기능 통합 후 8시간 상주 시험. 초기 개인 배포 전 24시간 시험을 수행한다.
- 입력이 없는 동안 지속적인 저장·네트워크 요청·복구 반복이 발생하지 않는지 확인한다.
- Win+D 100회, 창 표시·숨김 100회, 관리 창 열기·닫기 100회를 각각 시험한다.
- 탐색기 재시작과 절전 복귀는 사용자 작업에 영향이 있는 시험이므로 시점을 조율하고 별도로 수행한다.
- 실제 앱 종료 후 앱 프로세스·트레이 아이콘·파일 잠금이 남지 않는지 확인한다.

## 초기 판정 기준

아래는 지원 사양이나 성능 약속이 아닌 조사·출시 검토 기준이다. 최초 측정 후 현실적인 절대 예산을 기록한다.

- 반복마다 폐기한 창·편집기·이벤트·타이머·핸들이 누적되면 실패다. 일회성 런타임 증가와 구분한다.
- 안정화 후 동일 상태 GC 힙 증가가 기준값의 20% 또는 10MiB 중 큰 값을 넘으면 원인을 조사한다. 그 아래라도 지속적인 증가 추세나 남는 참조가 있으면 통과로 판단하지 않는다.
- 대표 환경에서 무작업 5분 평균 CPU가 전체 시스템 기준 1%를 넘으면 원인을 조사한다. 작업 관리자 등 측정 방식과 CPU 정규화 기준을 기록한다.
- 입력·서식 명령의 눈에 띄는 멈춤, 교착, 크래시, 데이터 손실, 종료 실패가 있으면 배포 전에 해결한다.
- 수치 변화의 이유와 장시간 시험 결과를 남긴다. 작업 관리자 화면 한 장만으로 '누수 없음'으로 판정하지 않는다.

## 0.9.3 프로세스 중단 복구 검증

0.9.3에는 시험 자식 프로세스만 저장 경계에서 강제 종료하고 새 프로세스에서 복구하는 8개 시나리오를 추가했다. [WM-004B](results/CRASH-04B.md)에서 최초 저장·정상 교체·손상 원본 보존·자동 저장 완료 응답 뒤의 결과와 미검증 범위를 구분한다. Windows CI가 별도로 실행한다. 장시간 상주/전원 차단 시험을 대신하지 않는다.

## 0.9.1 저장 수명 측정 결과

2026-10-22 격리된 메모 10개의 저장·숨김·재표시·보관·복원 100회와 5분 유휴/재실행 검증을 통과했다. 폐기 편집기 잔존 참조는 0개, GDI/USER 자원 누적은 관찰되지 않았다. 유휴 평균 CPU는 논리 CPU 8개 전체 기준 0.0586%였고 저장 본체/백업 파일의 해시·수정 시각이 유지됐다. [측정 방법·자원 추이·재현 명령](results/WORKSPACE-12A.md)을 참조한다. 8/24시간 전체 앱 시험과 실제 Windows UI 검증은 남아 있다.

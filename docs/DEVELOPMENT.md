# 개발 방식

## 운영 원칙

혼자 개발하는 프로젝트에 맞춰 칸반, 주간 스프린트, 인수 조건, 짧은 회고를 사용한다. 문서는 목표와 결과를 명확하게 하는 수준으로 유지한다.

## 칸반

GitHub Projects 연결 전에는 `BACKLOG.md`로 관리한다. 연결 후 이슈와 보드를 작업 상태의 기준으로 삼고, 로컬 문서에는 주요 목표와 결정만 남긴다.

| 상태 | 의미 |
| --- | --- |
| Backlog | 이번 주에 선택하지 않은 작업 |
| Ready | 이번 주 작업이며 인수 조건이 작성됨 |
| In Progress | 구현 또는 조사 중 |
| Review | 결과를 인수 조건에 맞춰 검증 중 |
| Done | 인수 조건, 검증 기록, 필요한 문서 갱신이 완료됨 |

- 동시에 진행하는 작업은 기본적으로 하나로 제한한다.
- 차단 여부는 상태와 별도로 표시하고 이유, 필요한 정보, 다음 조치를 기록한다.
- 큰 작업은 독립적으로 검증 가능한 단위로 나눈다.
- 보드 필드 후보는 상태, 우선순위, 작업 유형, 스프린트다. 필요한 필드만 추가한다.

## 주간 스프린트

- 실제 착수 시 시작일과 종료일을 일주일 간격으로 기록한다.
- 목표 하나와 필요한 작업 1~3개를 선택한다. 조사도 명확한 결과물이 있으면 작업으로 포함한다.
- 첫 스프린트는 바탕화면 부착 가능성 검증을 우선한다.
- 새 요구사항은 Backlog에 넣는다. 주간 목표를 바꾸면 이유와 제외할 작업을 기록한다.
- 종료 시 실제 동작 또는 조사 결과를 확인한다. 미완료 작업은 우선순위를 다시 판단한다.

## 작업과 인수 조건

작업 전에 사용자가 관찰 가능한 완료 기준을 작성한다. Codex에 작업을 맡길 때 작업 ID, 목표, 범위, 인수 조건을 전달한다.

```markdown
### 작업 ID: 제목
- 상태:
- 해결할 문제:
- 범위:
- 인수 조건:
  - [ ] 확인할 구체적인 동작 또는 결과
- 검증 방법과 환경:
- 결과 및 증거:
- 제외 범위 / 남은 문제:
```

## 완료 기준

- 모든 필수 인수 조건을 만족한다.
- 변경 영향에 맞는 검증을 수행하고 결과를 기록한다.
- 실행하지 못한 검증은 미검증으로 명시한다. 실제 화면 검증이 필요한 조건을 빌드 성공만으로 완료 처리하지 않는다.
- 기능 또는 실행 방법이 바뀌면 관련 문서를 갱신한다.
- 남은 문제는 후속 작업으로 기록한다. 필수 조건이 실패하면 Done으로 옮기지 않는다.
- 코드 변경 시 외부 입력, 저장 보호, 이벤트·타이머·핸들 수명을 영향 범위에 맞춰 검토한다. `SECURITY.md`와 `STABILITY.md`의 관련 검증을 기록한다.
- 공개 자동 배포 전 의존성·패키지 신뢰 검증과 반복·장시간 안정성 시험을 수행한다. 미검증 항목을 검사 완료로 표시하지 않는다.

## TDD 및 검증

저장·복원·데이터 변환처럼 자동 검증하기 좋은 로직에서는 필요할 때 실패하는 테스트 → 구현 → 정리 순서로 TDD를 연습한다. 단순 문서 수정이나 구현 내용을 그대로 반복하는 테스트는 추가하지 않는다.

바탕화면 부착, Win+D, 클릭 및 입력은 실제 Windows 환경에서 수동 검증한다. Windows 빌드, 화면 배율, 모니터 수와 결과를 기록한다. 자동 테스트는 이 확인을 대신하지 않는다.

## Git와 CI 도입 계획

현재 로컬 Git 저장소를 main 브랜치로 초기화하고 https://github.com/DongminKang0919/windows-desktop-notes.git 를 origin으로 연결했다. CI와 GitHub Projects는 아직 없다.

- `main`을 기본 브랜치로 사용한다.
- 작업별로 짧은 브랜치를 사용한다. 예: `feat/desktop-attachment`, `fix/note-restore`, `docs/readme`.
- 원격 저장소 연결 후 PR에 변경 내용과 검증 결과를 남기고 인수 조건으로 검토한다.
- 실행 프로젝트가 생기면 CI에서 빌드를 검증한다. 의미 있는 자동 테스트가 생기면 함께 추가한다.
- CI 결과와 실제 바탕화면 동작 검증 결과를 구분한다.

## 주간 회고: 10분

잘된 점과 막힌 점을 짧게 정리하고, 다음 주에 적용할 개선 하나를 선택한다.

```markdown
### 회고: YYYY-MM-DD
- 이번 주 목표 / 달성 결과:
- 잘된 점:
- 막힌 점과 원인:
- 다음 주에 적용할 개선 하나:
- 확인할 시점:
```

회고 주기는 운영 규칙이며 자동 알림은 설정하지 않았다.

# 버전 및 자동 업데이트 설계

2026-10-22 갱신. 현재 로컬 개발 버전은 0.9.0 prototype이다. 포스트잇 UI와 스키마 4를 추가했고 ZIP·설치 파일 생성과 로컬 시험 업데이트를 유지한다. 실제 설치본 간 업데이트·서명·업데이트 서버는 미검증 또는 미연결이다. 아래 자동 적용 주기는 후속 설계이며 현재 업데이트 동작은 마지막 절을 따른다. UI·저장 형식 변경은 [WM-013](results/POSTIT-13.md)을 따른다.

## 버전 관리

소스 이력은 Git, 배포한 앱은 릴리스 버전, 메모 저장 형식은 schemaVersion으로 구분한다.

| 구분 | 규칙 |
| --- | --- |
| 앱 버전 | MAJOR.MINOR.PATCH 형식. 개발 초기에는 0.x.y 사용 |
| 패치 | 기존 동작의 오류 수정. 예: 0.1.0 → 0.1.1 |
| 기능 추가 | 호환되는 기능 추가. 예: 0.1.1 → 0.2.0 |
| 정식 버전 | 핵심 기능과 배포·업데이트가 검증된 시점에 1.0.0 |
| 호환성 변경 | 1.0 이후 사용자·데이터 호환성을 깨는 변경은 주요 버전 증가와 이전 계획 기록 |
| Git 태그 | 배포 커밋에 v0.1.0 형태로 연결. 게시한 태그와 패키지를 같은 버전으로 덮어쓰지 않음 |
| 저장 형식 | schemaVersion을 별도로 관리. 앱 패치마다 증가시키지 않음 |

위 숫자는 예시이며 현재 배포 버전은 없다. 0.x에서도 데이터 호환성 변경을 릴리스 노트에 명시하고 이전 절차를 검증한다.

버전은 프로젝트 생성 후 공통 빌드 설정 한 곳에서 관리하고 앱 표시·패키징·릴리스 태그가 일치하는지 검증한다. DLL의 AssemblyVersion 등은 도구 규칙에 맞춰 매핑하되 사용자에게 보이는 제품 버전과 혼동하지 않는다. 업데이트 버전은 문자열 비교가 아닌 패키징 도구의 버전 비교를 사용한다.

## WM-010A: prototype ZIP 패키징

scripts/package.ps1은 공통 버전으로 Release 빌드·자동 검증 후 win-x64 framework-dependent publish를 수행한다. 실행 파일 버전과 x64 apphost를 검사하고 시작 안내·파일별 SHA256·소스 커밋 및 작업 폴더 변경 여부를 포함하는 manifest를 만든다. ZIP과 체크섬은 artifacts의 실행별 GUID 폴더에 생성하며 기존 파일을 덮어쓰거나 사용자 메모를 읽지 않는다.

.NET 10 Desktop Runtime x64 설치가 필요하다. 이 ZIP은 설치·업데이트 패키지가 아니며 코드 서명도 아직 없다. 파일 해시와 ZIP SHA256은 손상 검사이고 게시자 신뢰 검증과 다르다. 스키마 3과 앱 버전 0.6.0은 그대로 유지한다.

verify-package.ps1은 ZIP을 추출하지 않고 파일 목록·버전·해시·경로를 검사한다. test-package.ps1은 원본 보존 후 변조 복사본으로 체크섬·내용·경로·버전·출력 경계 거부를 확인한다. 수동 GitHub Actions 작업은 검증 성공 후 ZIP·체크섬만 다운로드용 artifact로 보관한다. 실제 원격 작업과 압축 해제본 실행은 후속 검토다.

참고: [Microsoft publish 방식](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [GitHub artifact 업로드](https://github.com/actions/upload-artifact), [로컬 검증 기록](results/PACKAGE-10A.md).

## 자동 업데이트 기본안

사용자가 자동 업데이트를 요구했다. 아래 적용 시점과 주기는 제안 기본값이며 실제 사용 후 조정한다.

1. 첫 설치는 사용자가 설치 프로그램으로 수행한다.
2. 정상 앱 시작 후 비동기로 업데이트를 확인한다. 상주 중에는 약 24시간마다 확인하고 트레이에 수동 확인도 제공한다.
3. 최신 정식 버전이 있으면 백그라운드에서 다운로드한다. 개발 빌드와 시험판은 정식 사용자에게 자동 배포하지 않는다.
4. 기본 적용 시점은 다음 정상 종료 후 재실행이다. 편집 중 강제 재시작하지 않는다.
5. 오래 상주하는 사용자를 위해 '저장 후 지금 업데이트'를 제공한다. 최신 변경 저장을 완료한 후 업데이트·재시작하고 창을 복원한다.
6. 저장 실패 시 즉시 업데이트 재시작을 중단한다. 다운로드 실패·오프라인이면 현재 버전으로 계속 사용한다.
7. 새 버전에서는 본문·서식·위치·숨김·휴지통 상태와 설정을 유지한다.

완전 자동 적용과 무중단 실행은 별개다. 실행 파일 교체에는 종료 또는 재시작 시점이 필요하므로 기본은 다음 실행에 자동 적용한다. 사용 중 자동 재시작이 필요한지는 별도 사용자 선택으로 남긴다.

UpdaterService가 확인·다운로드·대기 상태를 관리하고 앱 종료 조정자가 저장 완료를 확인한다. 패키징 도구의 시작 훅은 일반 WPF 시작, 데이터 로딩, 단일 인스턴스 처리보다 먼저 배치하는 방향으로 구현 시 문서를 재확인한다. 설치·업데이트 훅에서 정상 앱을 잘못 띄우지 않는다.

## 업데이트 파일과 사용자 데이터 분리

프로그램 설치 루트와 사용자 데이터 루트는 서로 겹치지 않아야 한다. Velopack의 설치 폴더는 교체·제거될 수 있으므로 후보 데이터 경로 `%LOCALAPPDATA%\WindowsMemo`를 그대로 설치 루트로 사용하지 않는다. 제품 식별자 확정 시 예를 들어 설치용 `WindowsMemoApp`, 데이터용 `WindowsMemoData`처럼 구분하고 실제 절대 경로를 검사한다.

- 메모, 설정, 로그, 백업은 패키지 교체 대상 밖에 둔다.
- 저장 형식 변경 전 백업하고 단계별 마이그레이션을 수행한다. 실패하면 원본을 보존하고 오류를 안내한다.
- 이전 앱 버전이 더 새로운 저장 형식을 읽을 수 없으면 조용히 덮어쓰지 않는다.
- 앱 롤백과 데이터 롤백은 별개다. 자동 다운그레이드를 기본으로 제공하지 않는다. 호환성 문제는 수정한 더 높은 버전 배포를 우선한다.

## 릴리스 흐름

1. 작업 인수 조건, 빌드·자동 테스트와 핵심 Windows 수동 검증을 완료한다.
2. 변경 내용과 남은 제한사항을 릴리스 노트로 작성한다.
3. 버전을 증가시키고 동일 커밋에서 설치 파일과 업데이트 패키지를 생성한다.
4. 시험 설치본으로 이전 버전 → 새 버전 업데이트를 확인한다. 개발 폴더 실행만으로 업데이트 성공을 판정하지 않는다.
5. 릴리스 태그 및 패키지를 게시한다. CI 빌드와 배포 게시를 구분하고, 초기에는 검증 후 게시한다.
6. 게시한 버전에 오류가 있으면 같은 번호의 파일을 교체하지 않고 다음 패치 버전을 배포한다.

초기에는 stable 채널 하나로 시작한다. 시험 배포가 필요해지면 별도 채널로 분리한다.

## 배포 전에 결정할 사항

- 공개 다운로드 가능 여부: 비공개 소스와 공개 배포 파일은 별개다. GitHub Releases가 공개되어도 되는지 정한다.
- 비공개 배포가 필요하면 인증된 배포 경로를 설계한다. 개발자의 GitHub 토큰을 배포 앱에 포함하지 않는다.
- 코드 서명 인증서와 예산, 릴리스 권한 및 배포 패키지 검증 방식을 정한다. 해시 검증과 게시자 신뢰는 다른 문제다.
- 업데이트 다운로드는 신뢰하는 HTTPS 배포 경로로 제한하고 도구의 무결성 검증 실패를 처리한다.
- 공개 자동 배포에는 SECURITY.md의 게시자·메타데이터 신뢰 검증을 적용한다. 코드 서명된 파일을 생성한 것만으로 적용 경로의 신뢰 검증을 완료 처리하지 않는다.

## 업데이트 인수 조건

- [ ] 설치한 이전 버전에서 더 높은 정식 버전을 발견·다운로드한다.
- [ ] 편집 중 강제 재시작하지 않고 다음 실행 또는 저장 후 수동 적용으로 새 버전이 실행된다.
- [ ] 메모 본문·서식·위치·숨김·휴지통 및 설정을 유지한다.
- [ ] 오프라인·잘못된 패키지·다운로드 중단이 현재 버전의 사용과 메모를 손상시키지 않는다.
- [ ] 저장 실패 시 업데이트를 위한 재시작을 하지 않는다.
- [ ] 데이터 마이그레이션 실패 시 원본과 백업을 보존한다.
- [ ] 제품 버전, 설치 패키지 버전, 릴리스 태그가 일치한다.
- [ ] SECURITY.md의 배포 보안 기준과 STABILITY.md의 반복·장시간 검증을 만족한다.

## 0.7.0 prototype 설치 준비 (WM-010B1)

Velopack와 vpk 1.2.161을 고정하고 앱 시작의 첫 동작으로 VelopackApp.Run을 배치했다. 설치용 ID는 WindowsMemoApp이며 기본 설치 루트는 %LOCALAPPDATA%\WindowsMemoApp, 데이터는 기존 %LOCALAPPDATA%\WindowsMemo\Notes다. 이 ID는 이후 업데이트에서도 유지해야 한다. 설치 파일 생성과 업데이트 적용은 구분한다. 현재 UpdateManager·원격 확인·다운로드·적용 코드는 없다.

package-installer.ps1은 검증된 ZIP payload에서 설치 EXE와 full nupkg 및 win 피드를 만든다. .NET 10 x64 Desktop 런타임 bootstrap과 시작 메뉴 바로가기를 설정했다. 설치기는 앱을 자동 실행하므로 설치 전 기존 앱을 저장 후 종료한다. 개발 폴더의 자동 실행 등록은 설치본으로 자동 이전하지 않는다. 설치본에서 기존 등록을 해제하고 재등록해야 한다.

수동 installer CI는 artifact만 생성하며 Releases 업로드는 하지 않는다. 파일 해시는 손상 확인용이다. 게시자 서명·공개/비공개 배포 방식·설치와 제거 시 데이터 보존·두 버전 간 업데이트·런타임 없는 머신 검증은 후속으로 남긴다. [검증 기록](results/INSTALLER-10B1.md).

참조: [Velopack 시작 훅](https://docs.velopack.io/integrating/overview), [CLI pack](https://docs.velopack.io/reference/cli/content/vpk-windows), [런타임 bootstrap](https://docs.velopack.io/packaging/bootstrapping), [설치 위치](https://docs.velopack.io/packaging/installer), [고정 패키지](https://www.nuget.org/packages/Velopack/1.2.161).

## 0.8.0 prototype 로컬 시험 업데이트 (WM-010B2A)

0.7.0의 설치 준비에 이어 UpdateManager 어댑터와 트레이의 수동 확인·다운로드·저장 후 적용을 구현했다. `--update-test-source <로컬 절대 폴더>`로 설치본을 실행한 경우에만 활성화한다. 외부 배포 주소와 인증 정보는 포함하지 않는다. full 패키지만 허용하며 downgrade와 prerelease는 거부한다.

UpdaterService는 중복 작업과 종료 후 적용을 차단한다. NoteWorkspace.SaveThenAsync는 모든 표시 메모를 저장하고 편집·생성을 막은 상태에서 적용을 호출한다. 저장 실패 시 적용하지 않으며 적용 요청이 예외를 던지면 편집을 복구한다. 로컬 피드·다운로드·적용 직전 캐시의 크기와 SHA256을 검사한다. 동일 계정의 파일 교체 경쟁이나 게시자 위조를 완전히 방어한다고 주장하지 않는다.

시작 훅에 SetAutoApplyOnStartup(false)를 적용해 다운로드된 시험 패키지가 다음 일반 실행 때 자동 적용되지 않게 했다. 현재는 명시적인 저장 후 수동 적용만 지원한다. 시작 시/24시간 주기 확인, 다음 정상 실행 적용, 원격 배포·서명은 후속이다. 설치본 두 버전 간 실제 적용과 데이터 보존, UI, 제거·런타임 bootstrap 검증도 남아 있다. [검증 기록](results/UPDATE-10B2A.md).

참조: [Velopack 적용 및 오류 처리](https://docs.velopack.io/integrating/overview), [업데이트 소스](https://docs.velopack.io/integrating/update-sources). API 호환성은 고정된 1.2.161 패키지와 Release 빌드로 확인했다.
